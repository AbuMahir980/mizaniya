# The artboard generator

Every board in `../canvas/` is produced from here. **It is committed, and that is
the point of it.** The original generator was about forty modules that lived in a
cloud container and were never committed — only the output was. The container was
reclaimed on 14 October 2026 and the toolchain went with it.

Nothing was lost, because the output *is* the source: each `.dc.html` carries the
whole stylesheet in its `<helmet>` and its theme as custom properties on the
`.mz` wrapper, and 246 of the 263 boards shared a byte-identical helmet. So this
does not rebuild the old toolchain. It does something that cannot rot the same
way:

**`mz.py` takes a committed board as a template and fills three slots in it** —
the title line, the frame's contents, and the note. The chrome, the fonts, the
tokens and the radii are never retyped, so a board drawn today cannot drift from
one drawn in September. A board is regenerated by running the script that makes
it; a board is *edited* by `patch_boards.py`, which asserts its match count
before it writes.

| File | What it is |
|---|---|
| `mz.py` | The system: the two frames, the primitives, the token swap, `write()` |
| `icons.json` | The fourteen icons, extracted from the committed boards by frequency |
| `recovery.py` | Everything ADR-013 created — the chooser, the keys, the gate, household |
| `build_pages.py` | The public pages whose *claims* changed: 20, 21, and the landing eight |
| `patch_boards.py` | Exact-string edits to committed boards, each asserting its count |
| `measure.py` | Every board's rendered box, into `sizes.json` |
| `manifest.py` / `build_manifests.py` | The two canvases, laid out from measured sizes |
| `shoot.py` | PNGs, at the names the docs already link to |

Run order after changing a drawing: the script that draws it, then `measure.py`,
then `build_manifests.py`, then `shoot.py`. The manifests carry each board's
width and height, so a note that grew by two lines will lay one board over
another if the measure step is skipped.

Both build scripts are idempotent. Running them twice gives the same two
manifests as running them once, which is not a nicety: a build script that is
only correct the first time is a build script that will be run twice.
